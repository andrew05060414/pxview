# PXView 依赖现代化路线图（暂不执行版）

> 状态：规划中（Planning Only）  
> 目标：为后续长期维护提供安全升级路径，避免“乱升一把梭”导致项目失稳。  
> 当前策略：**功能优先，迁移分阶段，逐步交给 AI 执行。**

---

## 1. 当前判断（先定原则）

这个仓库依赖栈偏老，且 `react-native`/Android 工具链与多条业务依赖耦合很深。  
结论不是“不能升级”，而是：

1. **不能在功能分支顺手升级**（高概率引入连锁问题）。
2. **必须拆阶段**，每阶段只做一类改动，并有明确回滚点。
3. **先保障可交付基线**，再做现代化迁移。

---

## 2. 基线冻结（Migration Baseline）

在任何迁移动作前，先把可用基线固定：

- 能通过核心测试（当前为 `jest` 全绿）。
- 能产出可安装 Android 包（debug 构建可行）。
- 小说内联图片修复链路已可用（当前已达成）。

基线分支建议：

- 功能主线：`codex/novel-inline-images-pr`
- 迁移专用：后续按 phase 新建 `migration/phase-x-*`

---

## 3. 风险分级（先动什么，后动什么）

## 低风险（可先做）

- 文档和脚本完善
- CI/验证脚本补强（不改 runtime）
- 小型 devDependency 升级（lint/format/test 辅助包）

## 中风险（分模块做）

- 某些独立库替换（例如工具库、解析类依赖）
- 非核心 UI 库版本微升（一次一个）

## 高风险（单独项目做）

- `react-native` 主版本升级
- Android Gradle Plugin / Gradle / JDK 组合升级
- React Navigation 代际升级
- 已停更原生库替换（涉及 Java/Kotlin/Manifest）

---

## 4. 分阶段路线（推荐）

## Phase 0 - 迁移护栏（1-2 天）

目标：先把“不会乱动”的流程建好。

- 新建 `MIGRATION.md`（可选）记录阶段与约束。
- 固化验证命令清单：
  - `npm test -- --runInBand`
  - `cd android && .\gradlew.bat assembleDebug --no-daemon`
- 约定分支规范：每个 phase 一个分支、一个 PR。

完成标准：

- 任何后续 phase 都能按同一套验证与回滚执行。

---

## Phase 1 - 可观测性与自动化补强（2-4 天）

目标：提高“升级失败可定位性”。

- 增加最小 CI（至少 test + android debug build）。
- 为关键功能补最小回归清单（登录、小说阅读、图片渲染）。
- 补充故障排查文档入口（已存在 notes，可继续积累）。

完成标准：

- 升级失败时能快速知道“坏在哪一层”（JS / 原生 / 打包）。

---

## Phase 2 - 低风险依赖清理（3-7 天）

目标：先清理“几乎不影响 runtime”的债务。

- 优先处理 devDependencies（eslint/jest/babel 辅助链的小步升级）。
- 清理无用包/脚本（有证据再删）。
- 维持 lockfile 策略一致（当前先不切换包管理器）。

完成标准：

- 开发体验提升，功能行为不变，回归全绿。

---

## Phase 3 - 中风险库替换与兼容（1-2 周）

目标：降低未来 RN 大升级阻力。

- 优先排查“已停更或兼容风险高”的库。
- 一次只替换 1 类库，严格保持可回滚。
- 每次替换后都跑同一套验证命令与手工用例。

完成标准：

- 关键业务功能不回退，依赖健康度提升。

---

## Phase 4 - React Native / Android 工具链升级（2-6 周，分段）

目标：从老版本平滑过渡到更可维护版本。

建议方式：

- 不跨太大版本，按“跳板版本”迁移（例如 0.63 -> 中间稳定版本 -> 目标版本）。
- 每次只做一个“平台层主题”：
  - RN 核心
  - Android Gradle/JDK
  - 导航/手势/动画生态

完成标准：

- 新工具链可稳定构建 + 核心功能回归通过。

---

## 5. 暂时不要动的内容（直到进入对应 phase）

- 不在功能分支修改 `react-native` 主版本。
- 不在同一个 PR 中同时改“业务功能 + 工具链升级”。
- 不在未建立验证护栏前大改 Android Gradle 组合。
- 不把本地调试产物（缓存、脚本、临时资源）带入迁移提交。

---

## 6. AI 执行模式（你可以直接照这个交给 AI）

每个 phase 用一个独立会话 + 独立分支，给 AI 的指令模板：

```text
目标：执行 Phase X（仅限本阶段范围）。
约束：
1) 不改超出阶段范围的依赖
2) 每次改动后必须运行固定验证命令
3) 失败时先回报根因，不做跨阶段修复
4) 输出：变更清单、风险、回滚点、下一步建议
```

分支模板：

- `migration/phase-0-guardrails`
- `migration/phase-1-observability`
- `migration/phase-2-low-risk-deps`
- `migration/phase-3-library-replacement`
- `migration/phase-4-rn-android-upgrade`

---

## 7. 包管理器策略（结合你的偏好）

你偏好 `pnpm`/`uv` 没问题，但该仓库当前是 npm lockfile 体系。  
建议：

- **短期**：先保持 npm 体系稳定，不在当前阶段切换。
- **中期（Phase 2/3 后）**：再评估是否切 `pnpm`，单独做一条“包管理器迁移”分支与 PR。
- **原则**：包管理器迁移不要和 RN/Android 大升级叠加。

---

## 8. 启动条件（什么时候开始迁移）

当以下条件满足时再启动 Phase 0：

- 当前功能需求压力降低（有迁移窗口）。
- 你可以接受阶段性投入（不是“一天搞完”）。
- 有空做最低限度回归验证（至少自动化 + 核心手工流程）。

在此之前，这份文档只作为路线图，不触发实际迁移改动。
